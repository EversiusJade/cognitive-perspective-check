# v0.2.0-rc.3 内容审查

日期：2026-10-11。这是静态内容审查，检查文字规则可能引起的风险，没有做模型行为实验。下列修订不表示已观察到模型失败，也不能证明效果提高。

## 检查与修订

- 适用范围仍是早期项目、设计和未定决策。普通事实问题与明确执行任务直接完成。
- 背景理解要抓住关键关系，只补问少量会改变方向的信息。按信息项计算问题数，不能用复合问句绕过上限；未知仍标为未知。
- 在同一目标和约束下比较。新目标或优先级是供用户选择的提议，历史上下文不能证明用户当前偏好。
- 视角应带来行动、标准或取舍上的差异，保留原路线的利益。框架已充分成立时，可以比较具体实现。
- 关键论据要能追溯到用户观察或来源；没有依据则标为假设，推演不能充当现实证据。
- 有依据才给出有条件的倾向。无法合理排序时，说明各条路线的成立条件和下一步；最小验证必须能区分路线。
- A 阶段在可能时直接交付用户需要的可用产物；B 阶段完成所选成果，不能用规格卡或流程模板代替。
- 保持少量问题、少量视角和单个深入分支，不增加固定表格，也不承诺后台 token 硬上限。
- 沿用安装入口与纯 skill 包。内容审查不能证明实际客户端安装、发现或自然调用已验证。

## 三种做法的取舍

纯澄清的入口短、容易结束，但理解需求后仍可能围绕同一预设展开，无法覆盖本项目的目的。

广泛多角色讨论能扩展立场，但角色不保证独立证据，也容易增加阅读和调用成本。

当前采用有限的连续流程：理解背景、检查双方预设、比较少量视角、给出条件判断，再交付用户选中的成果。它覆盖了项目主旨，也有误触发和 AI 强加框架的风险。

这次没有加入固定分析维度、角色委员会、无依据打分或新 skill。流程组合和成果边界更清楚了；相近项目也有少问、批判性思考和 AI 输出检查，尚无优于竞品的证据。

后续需要真实用户评价：理解是否准确、视角是否改变选择、产物是否可用、阅读负担是否合理。实际客户端还需观察明确调用、自然调用和连续纠正。这次没有新增这些试验，历史记录不能替代本版验证。
