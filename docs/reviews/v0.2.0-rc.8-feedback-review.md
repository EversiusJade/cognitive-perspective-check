# rc.8 外部建议 Review

日期：2026-10-17。建议来源：用户转贴的 DeepSeek 反馈。本轮对照 rc.7 核心规则、设计取舍和作者演示进行文本 review。

## 选择性采纳

| 建议 | 处理与理由 |
|---|---|
| 给执行任务明确判据 | 采纳，但不把动作动词当充分条件。按所需成果、方向是否已定和缺口是否阻塞区分 |
| 用“用户会厌烦退出”约束追问 | 不采纳施压句。改为单个关键未知、短句、同一未知的选项，确需多项时逐项显式列出 |
| 强制表格、固定格式、300 字 | 不采纳统一限制。要求内容容易扫读，完整交付和用户格式优先 |
| 先肯定用户预设，照顾沉没成本 | 改为承接真实目标，考虑可复用工作和未来切换成本；不强制夸赞，过去投入本身不证明继续合理 |
| 把简历改写请求识别为探索 | 不采纳该泛化。用户已确定岗位并要求改写时直接交付；不补造分析方法或经历 |
| 通过 UI、JSON、Zod 把流程框死 | 留作其他产品的设计选择，不给当前纯 Skill 增加依赖。格式校验不能证明分流、事实或建议正确 |
| “90分想法、60分鲁棒性、100分产品、护城河” | 不作为结论。没有评分量表、对照结果或实际竞争证据支撑 |

## 交付前 Review

检查了执行与探索边界、必要澄清是否仍可进行、提问限额是否冲突、已有目标是否保留，以及示例与证据的区分。修订保留了缺原文时的一句补问，避免“直接交付”被理解为不得澄清；保留“询问是否值得做”的探索分支，避免动作词误分流。已定架构和求职岗位的示例继续终止于用户所需成果。

同时核对核心入口、README、安装说明、版本说明和发布配置的版本及链接。本轮是静态文本 review，新增示例不是实测输出；没有运行新的客户端模型实验，也没有得出鲁棒性或 token 节省的量化结论。
