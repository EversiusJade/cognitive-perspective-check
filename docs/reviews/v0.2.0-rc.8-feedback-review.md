# rc.8 反馈 Review

日期：2026-10-17。反馈来自用户转贴的 DeepSeek 建议。对照 rc.7 核心规则、设计取舍和作者演示，做了文本 review。

## 对建议的处理

执行任务需要明确判据，但动作动词不足以判断。按用户要的成果、方向是否已定、缺失信息是否阻塞交付来区分。

“用户会厌烦退出”的施压句没有写入规则。追问改为一个短句问一个关键未知，选项围绕同一未知；确实需要多项信息时，逐项列明。

没有统一要求表格、固定格式或 300 字。内容应便于扫读，完整交付和用户指定的格式优先。

承接用户的真实目标，考虑可复用工作和未来切换成本。没有要求先肯定预设或强制夸赞，过去的投入本身也不能证明继续投入合理。

简历改写不能一概视为探索。用户已确定岗位并要求改写时，直接交付，不补造分析方法或经历。

用 UI、JSON、Zod 固定流程，可以是其他产品的设计选择，当前纯 Skill 没有因此增加依赖。格式校验不能证明分流、事实或建议正确。

“90分想法、60分鲁棒性、100分产品、护城河”没有评分量表、对照结果或实际竞争证据支持，不作为结论。

## 交付前 Review

检查了执行与探索的区别、是否仍能做必要澄清、提问限额是否冲突、是否保留已有目标，以及是否区分示例与证据。缺少原文时，仍可用一句话补问，避免把“直接交付”理解为不得澄清；用户询问是否值得做时，仍进入探索，避免仅凭动作词分流。已定架构和求职岗位的示例，都在完成用户所需成果后停止。

还核对了核心入口、README、安装说明、版本说明和发布配置的版本及链接。这是静态文本 review，新增示例不是实测输出；没有运行新的客户端模型实验，也没有得出鲁棒性或 token 节省的量化结论。
