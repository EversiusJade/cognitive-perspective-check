# 设计取舍

这些规则围绕同一个目标：检查会影响选择的预设，同时让讨论能推进到结果。当前发布版本为 `0.2.0-rc.6`，完整研究问题见 [研究目的](research-purpose.md)。

## 为什么限制提问

用户通常没有时间填写完整问卷。先提取已有信息，再检查某个未知的不同答案会不会改变行动。不会改变，就没有必要问。初始澄清累计最多三项关键信息，通常只需零问或一问；达到限额仍缺信息时，给出条件结论和能用的部分。

每轮重新确认方向，会打断已经得到授权的工作。因此只在新信息实质改变范围时重新对齐。“不知道”和“按你的判断”允许 AI 在说明假设后继续；没有回答则不能当作同意。

## 为什么只比较少量视角

视角的数量不代表分析质量。另一种理解只有改变行动、成功标准或收益与代价，才值得加入。通常比较两个，默认最多三个；不固定列举所有利益相关者，也不展开多层创意树。

原方案可能仍然有价值，需要给它最强的合理解释。证据不对称时，讨论篇幅也可以不对称。强行找反面，会让用户误以为支持程度相当。

## 如何避免 AI 替用户做主

用户明确的目标和硬约束是比较的基础。AI 补出的原因、方法和理解都可以修正，不应据此推断隐藏动机或性格。如果建议改变目标或优先级，需要明确提出。

AI 可以推荐一条路线，但要说明依据、适用条件，以及什么信息会让它改变判断。优先级未知或证据不足时，不必硬排最佳方案；可以先给出各路线成立的条件和能够区分它们的检查。剩下的价值取舍由用户决定。

## 如何把分析变成成果

已决定的行动与固定成果请求，在交付后结束。点名调用不改变这个分支；原因未经验证时，避免在成果中把它写成事实。确有实质影响时最多补充一句，不追加比较、测算或继续菜单。用户要求只给正文时优先遵守。

首轮需要给出可用的判断。用户已经要求一份方案、文案或文件时，尽可能直接交付，把必要的条件写进成果。用户选择继续后，默认围绕一个分支推进；明确要求更广范围时，遵守相应范围和预算。

| 用户选择 | 需要交付的内容 | 何时停止 |
|---|---|---|
| 验证一个假设 | 要看什么记录，什么结果会改变哪项行动 | 需要新证据且当前无法获得时 |
| 比较路线 | 与已确认目标有关的取舍、依据和适用条件 | 剩下是用户的价值选择或待查事实时 |
| 推演试点 | 默认最多三个关键节点，一个失败方向和可观察信号 | 所选情景的条件与后果已经说明时 |
| 制作或执行 | 所选范围内能用的方案、文案或文件 | 成果完成，或真实缺口已说明时 |

推演可以帮助找到待查事实，但不能证明预测会发生。新背景让旧视角失效时，替换受影响的部分即可。交付前做一次简短的目标、约束和格式检查，并区分计划中的动作与实际完成的工作。

## 成本与安装

单次有限检查和按需读取参考文件，是为了控制提问与阅读负担。流程本身不会自动启动搜索、多代理讨论或反复自我辩论；关键事实和所选任务需要时再使用工具。纯 skill 无法保证后台 token 节省，成本需要实际记录。

安装按客户端原生机制处理。仓库提供统一的 Skill ZIP 和手动安装说明，其他客户端的路径与实测状态分别记录，见 [兼容说明](client-compatibility.md)。

## 后续怎样改

优先处理阻塞明确任务、错误推定目标和没有实际差别的视角。规则应由真实失败推动，避免每发现一种可能性就扩写入口。

“关键假设、支持或削弱它的观察、如何检查、结果怎样影响选择”可以作为验证分支的短成果。目前保留一个入口，是否拆成独立 skill 需要实际案例支持。
