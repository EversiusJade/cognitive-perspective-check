# 本轮自我审查与收束结果

这是可复核的论点与取舍摘要，不是模型的逐字内部推理。目标是减少真实失败，同时保持安装与阅读简单。

| 审查问题 | 支持扩展的理由 | 限制或反证 | 本轮采用的规则 |
|---|---|---|---|
| 是否所有模糊问题都触发？ | 模糊需求可能遗漏关键背景 | 模糊表达也可能只需要一句改写 | 只有不同合理理解会改变建议或行动时校准 |
| 是否找出用户的“真正需求”？ | 需要区分目标与解法 | AI 也会强加自己的目标 | 提出暂定理解；明确目标不被擅自替换 |
| 是否逐项确认背景？ | 更完整的信息可能提升判断 | 无关信息增加追问和退出成本 | 提问前检验两种答案各会改变什么；通常零或一个问题 |
| 是否每轮重新确认方向？ | 可以保持用户参与 | 已确认的范围被反复打断 | 初始累计最多三问；只有新信息实质改变范围才重开对齐 |
| 是否必须形成对立面？ | 能打破原预设 | 假反对、假平衡可能误导 | 只保留会改变行动的替代框架，保留原方案的最强利益 |
| 是否只给问题让用户自己想？ | 用户参与能帮助理解 | 用户仍没有可用的第一步 | A 阶段必须给一份有用的有限判断和条件建议 |
| 是否把推演当论据？ | 可显示因果后果和潜在失败 | 情节合理不能证明真实世界会发生 | 推演标为假设，用来发现要查的事实，不制造证据 |
| 是否默认比较所有利益相关方？ | 可发现被遗漏的成本 | 固定维度增加阅读负担 | 只引入会改变本次选择的维度 |
| 是否做多角色辩论？ | 表面上提供多立场 | 未保证独立性，增加调用和呈现成本 | 单次校准同时检验用户与 AI；用户另有要求时才扩大 |
| 是否做“全平台一键安装”？ | 更容易传播 | 客户端发现机制各不相同 | 优先 Windows Copilot；共用目录、手动安装作明确补充 |
| 是否宣称严格省 token？ | 易理解的卖点 | 纯 skill 无法控制后台推理计费 | 只承诺行为约束；实测数据不足时不承诺节省比例 |

## 保留的两条不同产品方向

**方向一：轻量问题框架校准，当前主线。** 用户带着粗略需求来，AI 帮他看见几个关键解释怎样改变第一步。优势是接近真实使用入口、阅读少、能自然接续；难点是误触发和普通强模型已能做得不错，必须测出增益。

**方向二：显式的假设验证卡。** 用户已知道要比较什么，AI 只生成“关键假设、怎样证伪、最小验证、结果怎样影响选择”。它有更固定的交付物，可能更容易评价和收藏；代价是无法独立解决模糊需求理解。将来可成为单独 skill，当前没有增加第二个入口或要求用户安装。

两者不是上下级：第二种可以直接跳过需求校准，适合另一类用户。当前先验证主线，避免通过增加技能数量制造差异化。

## 运行分支

| 条件 | 本轮交付 | 停止条件 |
|---|---|---|
| 明确、已选定的任务 | 直接完成；有实质问题才加短提醒 | 请求的交付物完成 |
| 早期需求，框架可能改变行动 | 暂定理解、少量补问或条件分析、框架改变的后果、条件建议 | 用户已有足够信息选择，或需要事实验证 |
| 关键事实未知 | 最小验证方法或用户提供证据后的更新 | 无可获得的新证据时停止推测 |
| 用户选路线比较 | 只比较本次选择有关的少数指标 | 剩下是价值取舍 |
| 用户选沙盘推演 | 最多三个关键节点、一个可能失败方向、观察信号 | 所选情景已解释清楚 |
| 用户选择执行 | 目标、成功标准、约束、首步、修正条件的简短交接 | 所选范围内交付完成 |

## 成熟度与下一轮收束

当前定位为可安装候选版，不能把作者审查等同于已证明有用。成为稳定版需要实际客户端中发现、明确调用、自然调用、连续对话与任务执行的记录；还需要真实使用者判断理解是否准确、比较是否有帮助、是否增加不必要阅读。

下一轮优先依据失败修改：误触发和阻塞明确任务优先；错误推定用户目标其次；缺乏实际后果的替代框架再次。只有出现这些问题才增补核心规则。新的功能点先进入真实案例，不直接扩写入口。
