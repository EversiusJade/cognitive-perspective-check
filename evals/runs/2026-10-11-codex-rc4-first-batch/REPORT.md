## 这批能定位的问题

1. 基线已经能完成这两类任务。 C0 的两份回答见原文，分别给出短邀约和一句话润色；本批没有证明 skill 对探索性决策的增益。
2. 显式调用有额外公开说明。 两次 C2 都先解释如何使用 skill，再给最终答复；普通润色场景要求“只要一句话”，这一公开说明是应由人工评审检查的额外内容。C1 未出现公开说明，但没有文件读取事件只可记为加载状态未知。
3. 一次明确调用遇到运行环境问题。 邀约 C2 先用打包的 PowerShell 失败，再在 cmd 中误用 `Get-Content` 失败，最后用 `type` 成功读取正文。该回合的原生总 tokens 高于其他条件，但包含工具失败与多轮上下文，不能全部归因于 skill 指令，也不能据单个样本推广成一般成本比例。
4. 时延受连接重试影响。 每个回合都有宿主的连接重试通知。原生 wall time 包含这些等待，不能称为 skill 的纯推理时间；成功回合用量可见，未返回用量的内部重试消耗未知。原始失败和重试均保留，采集器没有额外替换样本。

后续应先解决沙箱中打包 shell 的可读运行路径，再以新配置登记重复采集。旧批次保留；不要把修复后的结果覆盖或合并为同一配置。本轮没有为了这些观察修改 `SKILL.md` 或冻结量表。

## 隔离与证据边界

本批的 MXC 命名权限配置默认禁读根目录，仅开放最小运行路径、空工作目录与系统技能，C1 / C2 另开放目标 skill。实际探测显示工作目录可读、C0 目标禁读、C1 目标可读，源码副本两组均禁读。两组都关闭搜索、Apps、Plugins、浏览器、多代理及已发现的 MCP；配置核对与探测见 [isolation-preflight.json](isolation-preflight.json)。网络探测失败本身不能排除服务不可用，因此同时保存了有效网络关闭配置。

五个系统技能在两组相同，目标之外的用户/插件技能统一禁用。预登记中的文字摘要误写“65 个用户/插件条目”：原列表的另外 65 个条目含 5 个系统技能，因此非目标用户/插件条目为 60 个。此处纠正摘要，实际启动配置及哈希没有改变；原登记文件保留。

只有邀约 C2 观察到成功读取目标正文。其他回合的加载状态为未知，不能从自述或回答风格推断。动态调用、遵守规则与效果提升仍需分别判断。

本批只涵盖两个单轮交付场景、一个配置、一次重复。没有探索性视角指标、真实用户采纳率、双人评分或统计增益结论；不能写“提升 X%”“节省 Y%”或“正式 pilot 已完成”。
