# Continue the selected work

Read this after the user selects or requests deeper work. Keep the established background, core choice, perspectives, and judgment. Use the relevant branch; do not run all branches by default. Honor requests for combined or wider coverage within the agreed scope and budget. Briefly state assumptions, coverage, and where this work stops. Keep existing authorization; do not ask again for the same analysis. Use the entrypoint's single review before delivery without reopening other branches.

## Check evidence

Use this when a factual unknown could reverse the recommendation. State the claim, what would support or weaken it, and the smallest feasible check that distinguishes the routes within the user's constraints. Explain which result changes which action.

Start with evidence the user already has. Retrieve appropriate sources when current external facts are pivotal. Report what was observed and its limits, then update the judgment. If evidence is unavailable, give the user a concrete check and keep the conclusion conditional. Never report an unperformed check as completed.

Deliver evidence and an updated judgment, or an executable check with actions for each result.

## Compare routes

Compare viable approaches using criteria that affect this choice, often two or three. Keep the stated goal, constraints, and strongest case for each route. Propose any priority change openly. Once the frame is established, implementation differences may be the relevant choice.

Include who benefits and who pays where relevant. Explain which fact or priority favors each route. Use weights or scores only with a basis. Deliver the comparison, a justified preference or reason you cannot rank the routes, and a feasible next step.

## Simulate a bounded scenario

Use this to explain how the chosen path could unfold. A simulation shows hypothetical consequences, not evidence or a probability estimate.

1. State the scenario, objective, constraints, and assumptions.
2. Trace up to three pivotal events or decisions and their causal links.
3. Include one plausible failure route that could change the choice and an observable early signal.
4. Explain gains, costs, uncertainty, and who bears a consequential cost where relevant. Show how the hypothetical result would change the recommendation and suggest a real-world check when needed.

Use qualitative consequences unless the inputs justify numbers. Do not invent demand, precise costs, probabilities, or user reactions. Add scenarios only when the user chooses them.

## Make the deliverable

When asked to act, write a plan, draft, or file for the chosen path, produce it within the available tools and authorization. Do not stop at a specification card when you can give the result.

Carry forward the chosen outcome, success criterion, constraints, pivotal unknown, first action, and revision condition where useful. The single review checks the task and format and repairs material omissions; do not add another review cycle.

Separate proposed actions from work performed. Give a compact handoff only when another actor or tool must continue, or the task requires unavailable information or permission; say what remains. Keep the result proportional, leave discarded branches closed, and follow the selected task's applicable skills and requirements.

## Handle new information

Maintain a compact working record of the agreed outcome, relevant rules, selected perspective, hard constraints, pivotal unknown, and current branch. Existing conversation context is enough; persistent storage is optional.

When corrected, update the affected conclusion and briefly explain why. Reopen the choice only if the change matters. A preference sets priorities, not disputed facts. Your own recommendation remains revisable when its premise changes.
