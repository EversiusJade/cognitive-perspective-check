# Deepen only the selected scope

Read this only after the user selects or explicitly requests deeper work. Continue from the established background, core decision, perspectives, and judgment. Choose the relevant branch; do not run all branches by default. Honor an explicit request for combined or wider coverage within the approved scope and budget. Briefly state assumptions, coverage, and the stopping point. Existing authorization persists; do not re-ask permission for the same analysis.

## Evidence check

Use when a factual unknown could reverse the recommendation. Name the claim, the observation that would support or weaken it, and the smallest feasible check that can distinguish the routes within the user's constraints. State which result changes which action. Use the user's available evidence first. If current external facts are pivotal, retrieve appropriate sources rather than filling gaps with speculation. Report the observation and its limits, then update the recommendation. If evidence cannot be obtained, provide a concrete check the user can run and keep the conclusion conditional; never report an unperformed check as completed. The useful output is evidence with a revised judgment, or an executable check with result-dependent actions.

## Route comparison

Use when the user is choosing between viable approaches. Compare only criteria that change this user's decision, often two or three. Preserve the same stated goal and constraints and the strongest case for each path; flag a proposed priority change. Once the frame is established, implementation differences can be the relevant choice. Where relevant, identify whose benefits and costs differ. Explain which priority or fact favors each choice. Do not invent weights or scores without a basis. The useful output is a comparison tied to the choice, a justified preference or explicit inability to rank, and the next feasible action.

## Bounded simulation

Use when the user wants to understand how a selected path unfolds. A simulation is a hypothetical consequence map, not evidence or a probability estimate.

1. State the scenario, objective, constraints, and assumptions.
2. Trace up to three pivotal events or decisions, explaining each causal link.
3. Show one plausible failure route that could change the choice and an observable early signal.
4. Describe what the path gains, costs, and leaves uncertain, including who bears a consequential cost when relevant. Say how the hypothetical result would change the recommendation and suggest a feasible real-world check when needed. Do not treat the simulated result as an observed outcome.

Use qualitative consequences unless inputs justify numbers. Do not invent market demand, precise costs, probabilities, or user reactions. Add further scenarios only when the user chooses them.

## Produce the selected deliverable

Use when the user asks to start acting, write a plan, draft content, or produce an artifact for the selected path. Complete that requested output within existing tools and authorization; do not stop at a specification card when you can deliver it. Carry the chosen outcome, success criterion, constraints, pivotal unknown, first action, and revision condition into the output only where useful. Check once that the result answers the chosen task in its requested format, then repair evident omissions without reopening analysis. Separate proposed actions from work actually performed. Give a compact handoff only when the task goes to another actor/tool or requires unavailable information or permission, explaining what remains. Keep the result proportional; do not regenerate discarded branches. Follow the selected task's applicable skills and requirements.

## New information

Maintain a compact working record from the conversation: agreed outcome, relevant rules, selected perspective, hard constraints, pivotal unknown, current branch. Use existing context; persistent storage is not required. When corrected, revise the affected conclusion and briefly explain the change. Reopen the choice only if the correction matters. A user preference selects priorities; it does not establish disputed facts. Your conditional recommendation is also revisable; avoid defending it after its premise changes.
